## 结论与证据层级

**实际换区崩溃仍未复现，根因未确定。** 新增的12个原始指令分支用例是离线资源状态验证，
不是12次真实换区，更不是崩溃修复验收。既有启动GUI异常与旧驱动读档异常继续分开归类。

当前引擎完整SHA256：`7e8649425217d3b99d52d11c679761a88c57b125c241b331aea5c25e00e3b15e`。
`tools/replay_scene_resource.py`只接受此摘要，复用既有PE映射和Unicorn基础设施。
查询、同步加载、Sleep和删除使用自有ABI边界；worker只重放dispatch块，
不执行真实队列遍历、并发调度、资源解码、绘制或文件加载。

## Verified：地图获取与worker不是同一加载路径

场景主链仍为 `62fc0 → 630cb → 68996 → 8a3f0 → 430d0 → 2a673`；
正常运行返回后 `6315b → 6aa2c` 清理。RVA均基于上述引擎。

地图获取 `2a673` 首先查询 `(type=8, id)`：

| 查询结果／状态 | 原始行为 | 返回后状态 |
|---|---|---|
| 无队列项 | `2a723`同步加载调用参数中的地图ID | 无项 |
| state=2 | `2a723`同步加载队列项ID；不等待，不标记删除 | 仍为2 |
| state=3，result非空 | 直接取result，`355d0`写state=4 | 4 |
| state=3，result为空 | `2a723`同步回退，再标记4 | 4 |
| 其余状态 | 每轮Sleep(30)，等到3，再按上述两分支处理 | 完成后4 |

`355d0`只是写入state字段，不是实际删除。`3299f`才移除列表项并释放记录；
`35530`原始指令只是返回传入指针，不是额外的生命周期保护或对象查找。

worker `32bbe` 的状态分发表（`32de8`）为：

| state | 原始dispatch行为 |
|---|---|
| 0／1 | type1读图片，type3调用`29c9d`；其他type不加载；末尾统一写3 |
| 2 | 不加载、不修改，结束本次扫描段 |
| 3 | 继续扫描下一项 |
| 4 | 调用`3299f`删除；结束本次扫描段 |

因此自有type8记录在state0／1时只变为3，result保持0，地图获取随后同步回退。
type3对照用例则确实抵达其加载边界并写入result。
这缩小了“worker并行加载type8地图”的解释空间，**没有排除共享队列或其他资源的竞态**。
不能把“存在后台线程”直接等同于“地图异步加载导致本次崩溃”。

如果注入“state1永不完成”，原始getter会持续等待，离线指令预算终止为
`bounded_wait_not_crash`；这仅验证等待分支，不证明游戏现场出现死锁或访问违规。

REA证据：worker `ev_f5a62ce78522272cb77680f19fba3544fa81c3034b58d5a2959d5f0029064424`；
getter `ev_7066ad7a84155d642a5e2c93bfd812bf761282cf3120bbd54291beb9a17d8ef0`；
作业 `ev_5179d59f76fb40b832a644fbf4e5ae30f0af021d157b3114f768ad65f5cc4ba0`。
反编译存在参数数量推断缺失，实际模拟按原始调用点的两个栈参数验证ABI，不照抄伪代码签名。

## 未验证假设与可证伪门槛

以下是取证优先级，不是已证明的概率排序：

1. **清理／重建期对象失效**：预测首异常或对象访问位于`6aa2c`及其析构链，
   或新场景使用旧对象；需同次换区的异常上下文、对象地址和释放历史。
2. **驱动纹理绑定／内部状态损坏**：预测当前驱动的首次异常涉及SetTexture路径和无效对象；
   需当前驱动身份与完整对象证据，旧驱动地址及合法COM持有引用不构成证明。
3. **后台共享队列竞态／等待异常**：预测异常或卡住线程落在`32bbe`、`3299f`、`32b3e`或`2a6ba`附近；
   需所有相关线程、队列项state/type及寿命证据。单线程注入时序不证明真实竞态。

本轮没有用户症状的红绿复现闭环，故不进入试修阶段。不加入换区冷却、全局解绑或吞异常。

## 玩家手动复现（约5—10分钟）

目标：先取得可命名的A→B换区与实际故障的对应关系，不要求推进到新剧情。
候选配置：现有`runtime/Play.cmd`和当前设置不变；保留已整合的GUI／楼梯守卫。
本节只提供步骤，不执行启动。`Play-baseline.cmd`同时撤去已有守卫，属于混杂变量，
本轮不作为首轮A/B比较。存档只在原有进度测试，不覆盖唯一存档。

1. 手动启动现有`runtime/Play.cmd`，读取靠近可往返出口的已有存档。
   记录存档槽、地图A/B画面名称、出口方位和当前设置；没有Field ID时不要猜ID。
2. 开始录屏或记录时间。等待地图可控制后再出发，正常A→B→A往返3轮。
3. 若稳定，再在可控制后立即返回，往返最多5轮。记录每轮方向、是否完成黑屏加载、
   首次出现异常的轮次，以及崩溃前最后可见画面。脚本传送、修改存档和连续强制输入均不使用。
4. 出现故障即停止；区分异常对话框、直接退出、卡死、黑屏、模型缺失，不统称“崩溃”。
   保留完整报错截图。卡住约30秒即记录，不强制继续试验。
5. 正常完成则从菜单退出；崩溃时关闭原异常对话框结束。卡死时由测试者手动关闭程序。
   下一次启动前保存`runtime/cache`现有日志；共享入口会覆盖上一会话日志。
   若已有转储，保留原件和时间，不上传商业内存到公开仓库。
6. 返回A/B名称、存档槽、设置、成功／失败轮次、时间、报错截图及日志。
   稳定时明确记录“此路线8轮未复现”，不据此宣称所有换区通过。

本轮不新增诊断副本、不引用旧入口作为可用采集方式。若日志不足，再针对已确认路线补充小型取证入口。

### 高置信方向与仍待验证项

同步清理／初始化期间，若没有其他呈现路径更新前台，上一帧就会保留；
这与补充症状相符。但嵌套资源函数、兼容层及Loading资源本身仍可能另有呈现行为，
静态外层调用顺序不是本次停顿时长或唯一根因的实测证据。

修复目标是**在进入耗时清理／加载之前，先绘制并提交一次Loading画面**，
随后沿原同步路径工作。它改善画面响应，不保证总加载时间缩短。
Loading资源应预先准备，不能到切换点再同步读取；绘制不能依赖即将释放的旧World／Camera。
具体入口、合法帧边界、失败处理和独立回滚仍需锁定，不直接把资源加载改为多线程，
也不以Sleep、空清屏或跳过清理代替修复。

下一次手动测试沿已有A/B路线录制一次即可，需包含触发前约3秒、整个停顿、
Loading出现和新场景恢复控制；记录“旧场景停止响应→首个Loading画面→新场景可控制”三个时间点。
若Loading从未出现，应明确记录，不按“Loading迟到”归类。未启动游戏、未安装呈现补丁。
